## 工具定位

CLI 配合其安装的 Skills 管理插件与 AI 应用的开发生命周期。能力、边界及变更确认要求见[CLI 介绍](<飞书项目开发工具 CLI 介绍.md>)。下文 `/meegle-plugin` 是原案例使用的 Skill 入口名称，需已安装并由实际 AI 工具识别。

<a id="b22a9c3f"></a>

## 适用范围

| 阶段 | 覆盖事项 |
| --- | --- |
| 身份与工程 | 登录认证，创建插件或 AI 应用工程 |
| 配置与代码 | 拉取、推送构成配置，生成或刷新模板，修改名称和描述 |
| 验证与交付 | 本地调试、构建客户端产物、发布插件版本或更新 AI 应用 |

自建后端的开发和部署属于独立工作。CLI 输出协议、权限清单和交接包，不代表已经实现 Webhook 处理、模型调用或业务数据写回。

## 准备环境

安装工具并登录目标站点：

```sh
npm install --global @lark-project/cli@latest
lpm login --site-domain https://project.feishu.cn
```

按浏览器提示完成 OAuth。安装时配套 Skills 会尝试注册到本地 AI 工具；重载工具后确认已识别。注册失败时按 `stderr` 中实际安装路径执行补装，详见[安装与登录](<飞书项目开发工具 CLI 介绍.md#b305b64f>)。

## 客户反馈分类 AI 节点

场景面向客户成功、售前、交付和工单团队，在反馈进入需求池前分流需求、Bug、任务和无需处理的信息。

> /meegle-plugin 创建一个“客户噪音过滤器”AI 节点应用。只读取“客户原声”和“客户级别”，判断为需求、Bug、任务或不需要处理；按客户级别、问题清晰度、业务影响、处理必要性四个维度进行 100 分制评分，输出立项建议、评分明细、原因和下一步建议。前端卡片只保留运行状态、输入说明、分析结果、立项建议和评分规则。服务端负责验签 Webhook、解析输入、调用模型、写回节点或工作项并完成节点。本次实现配置和前端，服务端提供交接包。

| 阶段 | 原案例流程 |
| --- | --- |
| 创建 | 确认站点和应用类型，使用 `lpm create` 创建 `ai_node` 工程 |
| 配置与界面 | 配置两个输入和 Web 卡片，生成 React 界面，检查类型、JSSDK 调用和构建 |
| 发布准备 | 完善名称、短描述、详情和分类，展示检查结果，再构建上传并按可见范围发布 |

评分各维度权重和结构化输出协议需在实际实现中明确。该提示词要求的是后端交接包，模型调用和节点完成逻辑尚需后端实现。

## 根据 PRD 生成产品手册的 AI 字段

输入 PRD 链接与生成提示词，由后端生成面向客户的产品手册，并把手册链接写回字段。

> /meegle-plugin 开发一个基于产品 PRD 生成产品手册的 AI 字段应用。输入为链接字段，输出也为链接字段，并允许配置生成产品手册的 Prompt。

流程为创建 `ai_field` 工程，配置“产品 PRD 链接”“生成 Prompt”和链接输出类型，预览配置后同步，再完善应用信息并发布。原案例是纯 Webhook 形态，没有 React 前端代码；不应额外生成仅为占位的 UI。

服务端需要依据交接包完成 PRD 访问、内容生成、文档输出及结果回写。发布配置或得到分享链接，并不证明这些业务能力已经可运行。

## 到场位置插件

原场景是在客户拜访或实施交付等任务中记录位置和时间。定位结果可作为业务记录的一部分，不宜仅凭页面定位就断言人员真实在场。

> /meegle-plugin 开发一个放在工作项详情页布局中的插件。点击后获取当前位置，以位置卡片展示，支持回显、重试和失败提示。先判断合适的点位并说明原因，再创建工程、配置点位、生成代码和启动调试。

原案例涉及 SDK 定位、存储、界面调整和发布，样式使用 BEM 命名。它也提到逆地理编码失败后的浏览器处理，但未提供具体实现；不能由此推断浏览器与 JSSDK 在各端都具有可互换的定位能力。应分别核对端支持、用户授权、存储隔离和错误处理。

原始资源：[位置插件演示视频](https://p9-arcosite.byteimg.com/obj/tos-cn-i-goo7wpa0wc/3a14e2c9a9cd490ea416e6d36641abc2)。

## 工作项导航页

导航页集中展示不同工作项类型，减少在各类型列表间来回切换。

> /meegle-plugin 从零创建一个工作项导航页插件，动态识别空间中的工作项类型，提供新建、查看、删除、搜索和分类浏览。先给点位设计与组件拆分，再实现 React 代码和调试发布流程。

原流程采用 Page 点位，生成 `WorkItemNavigatorApp.tsx` 等模块，通过 SDK 读取可用数据，再配置资源并本地调试。查看与导航可用的客户端 API，并不覆盖全部业务写操作；删除等动作需要对应权限和适当的后端实现。

点位与上下文见 [Page](<../points/导航功能页 Page.md>)；原案例中的 `lpm start --auto` 仅表示其工具版本的自动打开调试页方式。

## 需求热点词云

从工作项数据源提取中文高频词，按时间筛选，并通过词汇下钻关联工作项。

> /meegle-plugin 开发一个“需求热点词云”轻应用组件：基于工作项数据源做中文高频词分析，支持时间范围筛选，点击词汇联动查看工作项并打开详情。界面采用浅色、简洁布局。先给简洁方案，再实现并检查是否可发布。

原流程创建 `App.tsx`、`index.css` 等模块，配置 `liteAppComponent` 和数据源属性，完成词云与右侧列表联动，再运行本地预览和发布检查。分词、停用词和统计规则是实际业务实现的一部分，原案例没有给出可直接复用的算法。

原文提到 `lpm update`、`release`、`publish` 等动作，但没有给出完整参数和版本前提，不把这些名称拼成可盲目执行的发布脚本。

## 在已有工程增量迭代

此流程适用于新增按钮、Tab、视图或字段类型，也适用于修改现有逻辑。优先在包含源码的原仓库中操作，远端已发布产物不能恢复完整前端工程。

<a id="82cd7d9e"></a>

### 开始前记录可恢复状态

原实践建议在修改前提交当前可运行代码，并明确需求是新增点位还是修改已有点位。处理有未完成变更的仓库时，先查看差异并保存自己的工作边界，不把他人的未提交内容一起覆盖或回滚。

<a id="c4382697"></a>

### 需求表达示例

> /meegle-plugin 在当前插件目录中新增一个按钮点位，在工作项详情页提供“复制为新建”按钮。保留已有按钮和配置。

期望顺序是：形成配置变更清单，核对后同步后台，再在对应功能目录生成代码，最后启动本地调试。新建资源路径以工程配置为准，不能只按同类文件名选择已有实现覆盖。

<a id="e80e7938"></a>

### 三个检查节点

1. **配置推送前**：检查新增、修改、删除清单。远端同步会改变真实插件配置；特别检查本来要求新增的功能是否被错误归为修改。
2. **代码完成后**：启动本地调试，确认实际点位和交互，再决定是否发布。类型检查和构建通过不等于宿主调用正确。
3. **出现运行错误时**：提供 Console 堆栈、Network 的 4xx/5xx 响应和终端 stderr，按实际日志核对 SDK、字段和调用形态。

原流程的差异展示可整理为：

```text
[ADDED]    button [new_button] "Copy as new"
[MODIFIED] page   [main_page]  "Work item navigator"
           name: "Old title" -> "New title"
[DELETED]  tab    [old_tab]    "Retired details"
```

这些 key 和名称为展示格式的示例，不是待执行变更。删除项需要单独核对；诊断日志应保留定位信息，并去除凭证或不需要共享的业务内容。
